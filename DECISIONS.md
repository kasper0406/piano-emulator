# Decisions log

A running list of important decisions. Newest at the bottom. If you (human or agent) overturn one, strike it through and add the replacement.

1. **Language: Rust-only for v1.** Core DSP, audio I/O (via `cpal`, which wraps CoreAudio on macOS), and terminal UI all in Rust. Swift/ObjC only if we later need AUv3 packaging or tighter CoreAudio control than cpal offers.
2. **CPU SIMD, not Metal, for the real-time audio path.** GPU kernel dispatch latency/jitter is a poor fit for 128–256 frame audio blocks; Apple Silicon perf cores with NEON autovectorized f32 SoA loops are more than sufficient. Metal may be revisited later for *offline* tasks (batch rendering, automated preset tuning/optimization), where it is actually a great fit.
3. **Synthesis method: modal synthesis** (banks of exponentially decaying resonators per string), not digital waveguides. Rationale: direct, independent control of each partial's frequency (inharmonicity), decay, and amplitude — which is exactly what automated preset tuning needs; trivially SIMD-friendly; numerically robust. Nonlinear effects (hammer, phantom partials) are layered on top rather than emerging from a waveguide.
4. **Sample rate 48 kHz, f32, block size 128 frames internally.** cpal stream requested at lowest stable buffer size.
5. **Both real-time playback and offline WAV rendering** from day one. Offline rendering is required for automated spectral tests and later for automated tuning; "no input/output focus" is interpreted as: no MIDI input, no audio-device configurability, no plugin formats yet.
6. **Terminal UI = plain line-based REPL** for v1 (`n C4 90`, `chord ...`, `ped sus 0.5`, `demo`, `render out.wav`). No TUI framework yet.
7. **Two-polarization string model + 1–3 detuned unison strings per note** to get the characteristic double decay and beating, rather than faking it with envelope tricks.
8. **Dampers modeled as added (variable) damping, not hard gates** — this makes half-pedaling and damper-lift behavior fall out naturally. Notes above ~G6 have no dampers, as on a real piano.
9. **Sympathetic resonance via a global resonance bus** (sum of string outputs fed weakly back into all undamped strings' modal inputs) rather than a full N×N coupling matrix. O(N) cost, captures the audible effect.
10. ~~**No git history yet.**~~ Superseded 2026-08-13: the project lives at `github.com/kasper0406/piano-emulator`.
11. **SME (M4 Scalable Matrix Extension) noted but not used in the real-time path for now.** The modal-bank hot loop is an elementwise complex recurrence (diagonal state update), which doesn't map to SME's outer-product/matmul hardware better than NEON does. Two places it becomes attractive: (a) escape hatch if the NEON perf budget is blown — block-unroll the recurrence into a lower-triangular geometric-kernel matmul per mode (~64× FLOPs for matmul-shaped parallelism); (b) the future offline preset-tuning pipeline (batch evaluation of parameter candidates × notes), which is genuinely matmul/batch-shaped. User has SME experience (contributed SME matmul acceleration to Eigen).

The one remaining scaffold residue: hammer K/p tables are derived from physics rather than measured — the TUNING.md pipeline's job.

13. ~~**Contact time at the softest bass strikes reaches ~4 ms.**~~ **Superseded by 34.**
14. **The sympathetic resonance bus is read one block late.** Strings are driven by the previous block's sum, which removes the circular dependency between summing and driving. 2.7 ms of latency in a diffuse coupling path is inaudible.
15. **`ModalBank::set_damping_scale` takes one scalar per mode range**, as specified. The per-partial `damper_weight(f_k)` profile ended up needing a different shape per partial, so `set_damping_profile(&[f32])` was added alongside it; `string.rs` uses the latter and the range form remains for coarse changes.
16. **`Cargo.lock` pins `coreaudio-sys` to 0.2.15.** Versions from 0.2.16 require Cargo's `edition2024` feature, which the installed 1.84 toolchain does not support. Unpin once the toolchain moves to 1.85+.
17. **The audio stream refuses to open if the device cannot run at 48 kHz** rather than silently resampling or detuning the instrument. No resampler in v1.
18. **`tests/smoke.rs` covers the end-to-end invariants only** (bit-exact silence when idle, level and decay of a single strike, sustain pedal, pitch accuracy via rustfft, boundedness under dense playing, demo render). ~~The seven acceptance tests in SPEC.md land alongside the DSP modules they measure.~~ **They landed in `tests/acceptance.rs`, item 45.**
19. **The board output is the diffuse field alone, not a parallel dry path.** The spec writes `out = 0.65 * panned_direct + 0.35 * board(direct_mono)`. `board()` is read as a *response*: the mono voice sum is coloured by the 24 body resonators and that coloured signal is the FDN's only input, so the body's cabinet colour reaches the ear through the diffuse field rather than as extra mono in the direct path. Feeding the drive itself to the output would just collapse 35 % of the stereo image to the centre, which is what the scaffold's identity `board()` did.
20. **The board path is normalised to unity broadband gain** (~~`soundboard::BOARD_LEVEL = 0.70`~~ **1.44, see item 43** — measured with white noise through the full master chain, within 0.5 dB). Without it `board_mix` would change loudness as well as balance, and `OUTPUT_GAIN` would have to be re-measured every time the FDN is retuned. A unit test pins the normalisation.
21. **Body modes use Q 12-28, not the full 5-30 the spec allows.** Below Q ≈ 12 the 24 modes overlap into one broad low-frequency shelf instead of reading as resonances; a unit test asserts that every tabulated frequency is a local maximum of the bank's response. Their frequencies are also deliberately placed off the equal-tempered grid so no single key is emphasised.
22. **The master high shelf is first-order, -4 dB above 4 kHz.** The spec asks for "a gentle global high-shelf" without a direction; it cuts, standing in for the soundboard's falling radiation efficiency and for the fact that the modal string model has no such roll-off of its own. Being first order, the realised attenuation at 10 kHz is about -2 dB.
23. **The sympathetic-resonance drive is hard-clamped at ±1 N** (`resonance::DRIVE_CEILING`), and `set_coupling` clamps to `MAX_COUPLING = 0.05`. The loop-gain argument for stability (coupling × `1/(2 Z sigma_k)` ≈ 0.005 per hop) depends on the string parameter tables, so it is backed by a guarantee that does not: every modal pole is strictly inside the unit circle, so a bounded excitation cannot produce an unbounded output. The ceiling sits three orders of magnitude above normal playing and never colours the sound.
24. **The per-partial `damper_weight(f_k)` profile lives in `string.rs`, not `pedal.rs`.** The spec files it under "Dampers & pedals", but it is a property of the felt-on-string contact rather than of the pedal mechanism, and `string.rs` is where the per-partial sigma is assembled. `pedal.rs` answers only "how far down is this key's damper" (`damper_amount`), `string.rs` answers "and how well does it grip this partial".
25. ~~**`OUTPUT_GAIN` is still the scaffold's 16.0 and is now far too high**, driving dense passages into the safety limiter.~~ **Superseded by 42** (re-measured at 9.0).
25b. **The modal bank processes four modes per NEON vector, and culls in groups of four.** The complex recurrence is serial along the sample axis, so the mode axis is the one that vectorizes: the block loop walks the bank in chunks of `LANES = 4`, holding each chunk's state in registers for the whole block. The mode arrays are padded to a multiple of four with silent modes (`a = 0`, `g = 0`) so there is no tail case. Amplitude culling is therefore also per chunk — a group of four is zeroed and skipped only when all four are below `CULL_AMPLITUDE` — which is coarser than the spec's per-mode wording but never drops an audible mode. Measured: the whole 88-key compass ringing with the pedal down costs 31 % of one core in release (spec budget: < 50 %).
26. **Damper updates use a cubic Taylor form of `exp`, not `exp`.** The pole radius is stored as `r_base * exp(-extra_sigma / fs)`; a damper adds at most a few hundred 1/s, so the exponent stays below 0.01 where the cubic is exact to f32 precision. This is what makes it affordable to give all 80 partials their own damper weight and to re-evaluate it every block for the 10 ms damper ramp.
27. **The spec's T60 anchors are read as whole-note figures, not as the vertical polarization's decay.** A note is two polarizations; the quiet horizontal one outlives the vertical one and alone decides when the note reaches -60 dB. Taking 25 s / 12 s / 3 s / 0.6 s as the vertical bank's T60 would have made a C4 ring for 33 s. `string::vertical_decay_factor` solves `g_h exp(-rho sigma_v T60) = 10^-3 (1 + g_h)` for the vertical rate — a factor 2.64 with the spec's -12 dB / 3.4x slower horizontal — so the *audible* T60 lands on the anchor. C4's prompt sound accordingly decays in ~4.5 s and its aftersound carries the rest, which is what is measured on real instruments.
28. **The modal banks emit the string's force on the bridge, not its velocity, and a per-note `bridge_gain` table voices the compass.** For a hammer impulse `J`, mode `k` pushes the bridge with `4 f0 J sin(k pi x_strike)` — the wave impedance cancels and the fundamental frequency does not. Emitting velocity instead (the scaffold's convention) leaves the compass tilted 28 dB from C4 to C8. The remaining tilt after the change is the soundboard's business, so `string::bridge_gain_for` carries it: +8 dB at A0 falling to 0 dB by C4, calibrated by rendering fortissimo single notes. `EXCITATION_SCALE = 0.40` then sets the absolute level (mezzo-forte C4 peaks at -22.7 dBFS, the built-in demo at -4.8 dBFS, a twelve-note fortissimo chord reaches the limiter). ~~**`OUTPUT_GAIN`, `CULL_AMPLITUDE` and `IDLE_ENERGY` were left untouched and should be re-measured whenever the board's gain changes.**~~ **Done: the board's gain was wrong (item 43) and all of it was re-measured — items 42 and 44 carry the current values, and `bridge_gain_for` was re-voiced there.**
29. **The hammer works against an explicit agraffe reflection, replacing `CONTACT_STIFFENING` (item 12).** A force on the string launches `F/(2Z)` towards the agraffe, which returns it inverted after `t_ref = x_strike / f0`; that returning wave is what stops the contact point running away and ends the contact. Modelling it as a delay line reproduces the ripple that a real force pulse has, and with it the upper partials of the tone — a smoothed version of the same physics leaves the mid-range roughly 15 dB too dark by the fifth partial. But the delay is a positive feedback path of gain `k_felt t_ref / 2Z`, which passes 1 in the top octave at high velocity and diverges. Each strike therefore estimates its own peak felt stiffness up front and splits the reflection: the delay carries as much as keeps that loop gain below 1, and the surplus goes to `(1 - beta) 2Z / t_ref`, the spring the reflection is equivalent to after a few round trips. Below the top octave and up to a hard mezzo-forte the reflection is carried whole. A unit test asserts passivity (impulse `< 2 m v`, i.e. restitution below 1) over the entire key x velocity plane.
30. **The hammer meets the whole unison group, so it works against `unison * Z` and the pulse it publishes is the per-string share.** Without this the mid-range contact times come out roughly twice as long as measured ones, and it is the main reason a bass note (one string, soft) stays in contact three times as long as a treble note (three strings, stiff).
31. **Felt hysteresis is modelled (Hunt-Crossley, `F = K c^p (1 + lambda dc/dt)`) although the spec calls it optional for v1.** It costs one multiply, and without it the hammer leaves the string with almost all of its energy at low velocity. The factor is clamped to [0, 2] so a returning reflection cannot drive it into a runaway.
32. **The wave-impedance table was re-derived from `Z = T / c`** with a roughly constant tension across the compass: 6.5 kg/s at A0 through 2.2 at C4 to 1.7 at C8, replacing the scaffold's 4.0 / 1.6 / 0.5. The old treble values gave string masses several times too small.
33. **The strings of a unison group are coupled through the bridge inside `PianoString`** (`UNISON_COUPLING = 0.02` of the wave impedance, one block late as in item 14). This is what keeps the string the una corda hammer misses ringing, and it makes a group's decay uneven rather than a sum of three exponentials. The coupled force is a fixed fraction of the neighbours' bridge force, so it is unconditionally stable; measured, an unstruck sibling reaches roughly 1 % of the struck string's energy.
34. **Contact times run 0.4 ms (fortissimo C8) to 6 ms (pianissimo A0)**, against the spec's "typical 0.5-3 ms". Measured grands sit in the same range: contact lengthens both towards the bass and towards pianissimo, and the spec's figure is the middle of the compass at a normal dynamic, where the model gives 1.2-2.5 ms. The unit test asserts 0.35-6 ms.
35. **`tests/smoke.rs::struck_notes_sound_at_the_right_pitch` now searches a semitone band around the expected partial** instead of taking the loudest peak in the spectrum. Its own comment anticipated this: with a full partial set the loudest partial of A2 is the third, not the first, which is true of real pianos too.
36. **Automated parameter estimation plan agreed and written up in `TUNING.md`** (next workflow after v1 completes). Headlines: Salamander Grand v3 (Yamaha C5, lossless, 16 velocity layers) for stage-1 direct per-note estimation from partial tracks; MAESTRO v3 (Disklavier audio + note-accurate MIDI incl. pedal CC) for stage-2 interaction-parameter fitting via replay — no score alignment needed; YouTube-style recordings demoted to validation only (lossy codecs destroy the evidence). Loss = multi-resolution log-mel STFT + feature losses, with a jointly-fitted static "recording chain" EQ absorbing room/mic coloration. Engine prerequisites: preset extraction to serde files, per-note f0 table (stretch tuning), MIDI replay rendering. Hard gate: estimators must recover known parameters from our own engine's renders (self-calibration test) before touching real data.
37. **A silent string is now rendered whenever its dampers are up and the resonance bus has something to give it.** The engine used to skip every idle voice outright, which meant a string that had not been struck could never pick anything up — the sympathetic-resonance bus reached only strings that were already ringing, and the spec's acceptance test 5 (an unstruck C3 answering a struck G4) was unreachable. `Voice::process` now returns whether it rendered anything and owns the decision itself: it runs when it is ringing, or when `ResonanceBus::is_active()` and its damper target is off the strings. The bus gate is not a magic number — `is_active` compares the bus peak against the level at which `coupling * bus` could lift a mode past `CULL_AMPLITUDE`, so a voice is only woken when it could actually become audible. Cost: with the pedal down and anything ringing, all 88 voices run, which is the spec's own worst case (measured 39.5 % of one core, budget 50 %).
38. **The unison strings of a group get uneven detunings and uneven shares of the hammer's force** (`string::detune_ratio`, `string::strike_share`). Three identical strings at evenly spaced detunings sum to *exactly zero* twice per beat cycle: the measured C4 fundamental fell 60 dB into a null every 1.2 s and came back, which is heard as the note pumping to silence. The patterns are `[-0.5, 0.11, 0.5]` of the spread with force shares `[1.09, 1.0, 0.91]`, giving incommensurate beat rates and a beat depth of about 10 dB. Each share row averages to 1 and is paired with a detune pattern whose amplitude-weighted centre is nominal pitch, so the group as a whole is neither louder nor out of tune; a unit test pins both. The horizontal polarization's offset also varies per string (0.35 / 0.52 / 0.27 Hz) so the two polarizations cannot null together.
39. **Unison detuning is specified in cents, not hertz** (`StringParams::detune_cents`, 3.5 cents wide in the bass falling to 2.0 in the treble). Two strings of a unison differ in tension and `f_k ∝ sqrt(T)` for every partial at once, so the mistuning is a ratio; the spec's "±0.1-0.5 Hz, slightly wider in treble" is the same few cents read at the two ends of the compass. Taken literally in hertz it left A2's unison 6.6 cents wide — audibly sour, and wider than the ±3 cents the spec's own tuning test allows, which is how the deviation was found. The resulting hertz spreads (0.28 Hz at C2, 0.45 at C4, 2.4 at C8) are inside the spec's range.
40. **The spec's tuning test is measured on the attack, not the sustain.** Three strings a couple of cents apart are closer together than any window can resolve, so they merge into a single spectral peak; while they are still near in phase that peak sits at the group's real pitch, but later in the note the merged lobe is lopsided and the peak wanders by 2-3 cents. `tests/acceptance.rs` therefore analyses 0.05-0.65 s (errors within ±1.7 cents across all three test notes and partials 1-8) rather than a window spanning several beat periods. A tuner listens to the attack for the same reason.
41. **T60 is measured from a running maximum of the band envelope.** A unison group's envelope is not monotonic, so a first-crossing detector reports the first beat null rather than the decay time — it read C4 as 4.75 s where the design is 12 s. `tests/acceptance.rs::t60` demodulates the partial to an envelope and takes the last time a 1.5 s running maximum is still within 60 dB of the peak, i.e. the last moment the partial is audible. C4 measures ~10 s against the spec's 8-20 s window, C7 ~1.1 s against 0.3-2 s.
42. **`OUTPUT_GAIN` re-measured at 9.0 (was 16.0, item 25).** Calibrated through the finished chain so that the loudest thing a pianist can do — ten notes at fortissimo, struck exactly together — arrives at the safety limiter's -1 dBFS threshold rather than 6 dB past it. Mezzo-forte C4 now peaks at -19.5 dBFS, a single fortissimo note at -10, the built-in demo at -2.8 with the limiter never engaging, and 30 s of dense random playing at -6.5 dBFS peak with DC at -125 dBFS. `CULL_AMPLITUDE` and `IDLE_ENERGY` are expressed in terms of `OUTPUT_GAIN` and followed it automatically.
43. **`soundboard::BOARD_LEVEL` re-measured at 1.44 (was 0.70).** The original white-noise calibration of item 20 drove the board at full scale, so the safety limiter was inside the measurement and flattened both paths; with the excitation dropped to where the limiter never engages, the board path turned out to be 6.3 dB below unity. The test now excites at `0.05 / OUTPUT_GAIN`. The audible consequence is a distinctly more present diffuse field at the spec's 0.35 mix.
44. **`string::bridge_gain_for` re-voiced to flatten the compass**: +6.5 dB at A0 through +2.6 at C4 to +0.4 at C6 and +2.0 at C8. Measured on single mezzo-forte strikes, A0 / C2 / C4 / A4 / C6 / C8 now peak within 1.0 dB of each other (was 3.8 dB, with the midrange the quietest), and the chromatic sweep in `renders/scale.wav` spans 3.4 dB across the whole keyboard.
45. **The acceptance tests live in `tests/acceptance.rs`, the invariants stay in `tests/smoke.rs`.**
46. **`examples/analysis_render.rs` renders a measurement corpus into `renders/analysis/`** (65 WAVs: T60 holds, partial-analysis strikes, velocity ladders, a compass sweep, pedal/halo phrases, click-hunt transitions, ff chord blocks) — not part of the instrument, kept so audio-quality measurements are reproducible. An independent 2026-08 analysis of that corpus found every SPEC window met (partial residuals ≤ 1.3 cents vs the inharmonic model, T60 anchors 26.8/12.0/3.1/0.60 s at A0/C4/C6/C8, velocity→brightness monotonic at all four probe keys, pedal halo present and pedal-up silent, zero clicks, peak ≤ 0 dBFS, DC ≤ −90 dB) with two plausibility notes: (a) fundamental-band beat nulls on held C4/A2 reach 25–47 dB below the local envelope maximum — deeper than item 38's ~10 dB design figure — though at low absolute level (−90 dBFS and below), with whole-note envelope ripple of 10–14 dB p-p; (b) between item 44's calibration keys the compass dips: A1-region keys 27–33 sit 2.2–3.2 dB under their C1/C2 neighbours, total vel-80 span 4.5 dB. All seven of the spec's tests are implemented, split into ten `#[test]`s where the spec bundles several assertions (decay sanity becomes T60 plus release; the pedal test gains a half-pedal case; sympathetic resonance is tested both at bank-energy level and audibly). The performance test is `#[cfg_attr(debug_assertions, ignore)]` rather than `#[ignore]`, so `cargo test --release` runs it without a flag and `cargo test` skips it with a reason.
47. **`Engine::process` accepts any request length and produces the same sample stream regardless of how it is cut up.** The engine's state can only advance a whole `BLOCK`, so a request that is not a multiple of 128 now leaves the unconsumed tail of the last rendered block in a small remainder FIFO that the next call emits first. It used to render a full block and throw the tail away, which both clicked (a 16x jump in sample-to-sample difference at every call boundary, measured with 100-frame calls) and slipped time by the discarded fraction. The live path only escaped this because `audio.rs` asks for 256 frames; a device whose supported range clamps that to a non-multiple of 128 would have clicked continuously. `engine::tests::the_output_does_not_depend_on_the_request_length` pins the invariant sample-exactly for chunk sizes 1, 70, 100, 128, 129 and 333.
48. **Post-workflow review pass (Claude, 2026-08-13) applied three fixes.** (a) `audio.rs` now takes the buffer-size range from the config the stream is actually built with, not from `supported_output_configs().next()` — the first iterator entry can be a different format/channel count whose range is invalid for the chosen config. (b) The `OUTPUT_GAIN` doc in `types.rs` no longer claims the internal unit is string velocity (stale since item 28) and carries the current -19.5 dBFS mezzo-forte figure. (c) The stability discussion in `resonance.rs` was rewritten for the bridge-force signal convention; the loop-gain conclusion was re-derived and stands (worst-case slow bass partial answers with ~1 signal unit per unit of drive, so a hop is ~coupling ≈ 0.012, two orders below self-sustainment). Remaining accepted-as-is from verification: deep late-sustain beat nulls (item 46a, revisit with measured detune data from the TUNING.md pipeline rather than by hand), the A1-region 2-3 dB compass dip (46b, same), culling ineffective inside awake unison groups (performance headroom only, budget met at 31-40%), and a handful of currently-uncalled preset-mutation APIs (`ModalBank::set_mode` and friends) kept deliberately for the tuning pipeline.

49. **The package is a cargo workspace: `engine/` (the crate, still `piano-emulator`), `presets/` (versioned preset files), root manifest with `members = ["engine"]`.** `TUNING.md`'s layout, minus the `tuner/` crate, which is being built separately. The crate name and module paths are unchanged, so nothing that imports `piano_emulator::` moved. `[profile.*]` lives in the root manifest because cargo only honours profiles from the workspace root. Dependency versions have to respect a toolchain without `edition2024`: `Cargo.lock` already pinned `coreaudio-sys 0.2.15` for that reason, and adding `toml` needed `indexmap 2.7.1` / `hashbrown 0.15.5` pinned for the same one (the current releases of both are edition 2024). `serde`, `toml 0.8` and `midly 0.5` (default features off — its `parallel` feature pulls rayon, and parsing a MIDI file is not a hot path) are the new dependencies.

50. **Every tuning number is now data: `preset.rs` owns a serde `Preset`, and the DSP modules hold none.** `StringParams`/`HammerParams` are per-note views the preset hands out; `PianoString`, `Hammer`, `Soundboard`, `ResonanceBus`, `Voice` and `Engine` take what they need at construction and never look at a table again. The per-note quantities are stored as **88 explicit values**, not as the anchor curves they were written as: automated estimation produces one number per note (only for the notes it could measure, with the rest interpolated), which a curve cannot express. The curves survive as the code of `Preset::default`, which is both the v1 instrument and the sane way to hand-write a new preset — edit the anchors, `piano-emulator preset out.toml`, tune the numbers. Proof that the extraction changed nothing: the demo rendered by the v1 commit (`a05d7f3`) and the demo rendered today through `presets/default.toml` are **byte-identical WAVs**, and `tests/preset.rs` pins the file against the built-in default sample-exactly on every run.

51. **Preset floats are written as the shortest decimal that reads back as the same `f32`.** serde would widen `0.35f32` to `f64` and write `0.34999999403953552`; every scalar in the file would look like that, in a file humans are expected to read and edit. `preset::short` formats through `f32`'s own Display (the shortest round-tripping form, at most nine significant digits) and re-parses it as `f64`, which TOML then prints as `0.35`. Reading is the plain `f64 -> f32` serde already does — a decimal of nine significant digits converts through `f64` to the `f32` it came from — and `preset::tests::the_default_preset_round_trips` asserts the whole 1100-value round trip is bit-exact rather than trusting that argument.

52. **A preset is validated when it is loaded, not when it is played.** A preset file is untrusted input that becomes resonator coefficients and the coefficients of an ODE integrated on the audio thread, and the DSP has no other guard: a negative `sigma` is a pole outside the unit circle, a negative `B` puts a square root of a negative number in the partial layout, a zero hammer mass or felt stiffness divides by zero inside the contact model, a zero `Q` divides by zero in the body bank. `Preset::validate` therefore checks every table's length (88) and sign, unison counts in 1..=3 with matching layout rows, a strike point strictly inside the string, and positivity of every scalar the code divides by — and names the offending field in the error, so `--preset` fails on the command line instead of mid-render.

53. **The `f0` table is the tuning.** `Preset::notes.f0_hz` is what every "what pitch is this key" question in the engine reads — string layout, and the hammer's agraffe round trip `x_strike / f0`, which follows the tuning with it. `types::note_to_freq` stays as the equal-tempered formula and is now only the generator of the default table, so `presets/default.toml` is neutral and a Railsback-stretched instrument is an ordinary preset. Nothing else in the engine calls it.

54. **`types::OUTPUT_GAIN` and the two culling thresholds derived from it stayed constants** rather than moving into the preset with everything else. `CULL_AMPLITUDE` and `IDLE_ENERGY` are compile-time constants inside `ModalBank`'s inner loops, and they are expressed in terms of `OUTPUT_GAIN` precisely so a level change carries them along (item 42). Making the master level a preset field would mean threading two runtime thresholds through the hot loop to buy a knob that duplicates what `excitation_scale` and `bridge_gain` already do. Deviation from `TUNING.md`'s "all hardcoded constants": the master output level is deliberately not one of them. The FDN's delay lengths, the DC blocker and the limiter threshold likewise stayed in code — structure, not voicing.

55. **MIDI replay reads note on/off on every channel, CC64 as a continuous sustain, CC66 sostenuto, CC67 una corda, and the tempo map** (`midi.rs`, `midly`). Sustain is passed through as `value / 127` because that is the whole point of the engine's continuous damper model: a Disklavier recording's half-pedalling must reach the dampers as the fraction it was played at. Sostenuto and una corda are switches at 64 — those two pedals are levers that either catch or do not. Tempo is a piecewise-linear tick→second map built from every `SetTempo` in every track, evaluated in `f64`; ticks are merged across tracks with a stable sort so simultaneous events keep file order (a note off written just before a note on of the same key must stay that way). Format 2 files are rejected rather than played wrongly. **Deviation:** events are placed on the sample they belong to but take effect at the start of the 128-frame block containing it, so replay timing is quantised to 2.7 ms. That is a property of the existing event path, not of the loader — the engine's state can only advance a whole block (item 47), so a live keyboard has exactly the same granularity — and sub-block scheduling would mean offsetting hammer pulses and damper ramps inside the block, on the real-time path, for stage 2's benefit alone. Revisit if the stage-2 loss turns out to see it.

56. **CLI and REPL surface.** The binary gains subcommands that never open the audio device — `piano-emulator render <out.wav> [demo | <file.mid>]` and `piano-emulator preset <out.toml>` (writes the current preset out; this is how `presets/default.toml` is regenerated) — plus the global `--preset <file.toml>` and `--duration <s>`. With no subcommand it plays interactively as before. The REPL's `render <out.wav> [demo]` learns a third form, `render <out.wav> <file.mid>`, distinguished by extension, and renders with the preset the live engine was built from, so what you write to disk is what you are hearing. Argument parsing is 40 lines of hand-rolled matching rather than a dependency; the surface is three commands and two flags.

57. **`tuner/` is a standalone cargo package, not a workspace member.** It carries its own empty `[workspace]` table so cargo does not try to fold it into the root workspace, and its own `[profile.*]` (the same opt-level-3 dev profile the engine uses — long FFTs are unusable unoptimised). Two reasons: the tuner does not depend on the engine crate at all (it analyses recordings, whoever made them), and the engine's dependency graph stays as small as `SPEC.md` asks while the tuner is free to pull in decoders, resamplers and FFTs. `cargo test --release` at the root and inside `tuner/` are independent, and both are green. `TUNING.md` sketched `tuner/` as a workspace member; this is the deviation.

58. **Tuner dependencies: `hound` + `claxon` for decode, `rubato` for resampling, `rustfft`, `serde`/`serde_json`.** `claxon` over `symphonia` because the tuner only ever reads two lossless containers and `symphonia` is a demuxer framework with a much larger surface. `serde_json` needs its **`float_roundtrip` feature**: its default float parser loses up to one ULP, which would mean an estimator run from a cached trajectory file differing in the last bits from a run that recomputed it. All versions resolve on the 1.84 toolchain without `edition2024` (item 16).

59. **STFT magnitudes are sinusoid amplitudes, and a frame is timestamped at the centre of its window.** Each frame's spectrum is divided by half the window's coherent gain, so a partial rendered at amplitude `A` reads `A` — trajectories are then in the units of the signal and an estimator never has to know the window length to interpret them. Centre timestamping is what makes the decay correction below exact, and it is the instant a symmetric window's measurement actually describes. Only fully covered windows are analysed: a partially filled window measures a shorter signal at the wrong amplitude, and nothing downstream can undo that.

60. **The tracker divides the windowing bias out of decaying partials.** A Hann-windowed frame does not measure the envelope at the window centre, it measures the window-weighted mean of the envelope, and for `a(t) = exp(-sigma t)` that is larger by exactly `G(x) = sinh(x)/x * pi^2/(pi^2 + x^2)` with `x = sigma T / 2`. At the specified 2^16 window (1.37 s at 48 kHz) a partial with a 3.5 s T60 reads **60 % high** — far outside the 5 % the estimators need. The tracker therefore estimates `sigma` locally from the track itself (least squares on `log a` over the points within half a window) and divides `G` out. A constant `G` biases only the intercept of a later log-linear decay fit and not its slope, so decay-rate estimation was never at risk; what the correction buys is a correct absolute envelope — which the strike-spectrum, strike-position and hammer estimators all read — and an unbiased slope where `sigma` itself varies with time, i.e. exactly the two-exponential case `TUNING.md` wants fitted. `hann_decay_gain` is public and unit-tested against numerical integration.

61. **Track association is seeded by the inharmonic model and capped by partial spacing.** Each partial `k` gets a window around its predicted `f_k` whose half-width is the smaller of 60 cents and 0.45 of the gap to the nearer neighbouring predicted partial — above `k ≈ 20` the spacing cap binds, and it is what guarantees two partials can never compete for the same peak. Inside a window the candidate nearest the prediction wins, but only among candidates within 20 dB of the loudest one in that window: a Hann sidelobe is 31 dB down and can sit closer to a stale prediction than the true peak does. Proposals from all tracks are pooled and taken in order of increasing error so no peak is claimed twice. After a match the prediction follows the measurement, so the measured frequencies are free to disagree with the seed — that disagreement is what the `f0`/`B` estimator fits, and a test pins that a seed a semitone flat with `B = 0` still returns the rendered frequencies to within 0.05 Hz.

62. **Measured tracker accuracy on synthetic signals.** Twelve partials of a stiff string (`f0 = 110.31 Hz`, `B = 3.7e-4`, `sigma_k = 0.7 + 1.2 (f_k/1000)^2`), 40 dB SNR white noise, seeded 12 cents flat with the wrong `B`, 341 ms window / 10 ms hop: **worst-case frequency error 0.045 Hz** (median 0.005) and **worst-case amplitude error 1.7 %** (median 0.1 %) over every frame where the partial stands 26 dB above the worst noise peak the same transform produces. `TUNING.md`'s bar is 0.1 Hz and 5 %. Noiseless single sinusoid: 4.6e-3 Hz, 0.2 %. An A0-like case (20 partials 27.6 Hz apart, 6 s) at the full 2^16 default window meets the same bounds. The accuracy region is defined against a *measured* noise floor — white noise put through the same STFT — rather than a formula, so the tests state what the window they actually use can see.

63. **`tuner/src/synth.rs` is public, not a test module.** Sums of decaying sinusoids with known `f`/`a`/`sigma` plus seeded Gaussian noise (SplitMix64 + Box-Muller, so no RNG dependency and reproducible failures). The estimators land next and need exactly this ground truth; making it library code rather than a `tests/` helper means they share one generator with the tracker's tests. It renders the *model* the estimators assume, so a test passing against it says "the estimator inverts its own model" — the assumption itself is what `TUNING.md`'s self-calibration gate, running over the engine's own renders, is for.

64. **`rubato`'s `SincFixedIn` output is already time-aligned; `output_delay()` must not be trimmed off it.** Measured with an impulse and with tones from 100 Hz to 15 kHz: output frame `j` is input time `j * fs_out / fs_in`, residual after fitting the tone away is 150 dB down, amplitude exact, and the only deviation is a constant 0.084-frame (1.8 us) offset, identical at every frequency — a pure delay, not dispersion. Skipping the reported 139-frame `output_delay()` on top of that shifts everything by 2.9 ms. `audio::tests::resampling_preserves_the_position_of_a_transient` pins the alignment, because it is a property of the dependency rather than of our code.

65. **Test fixtures live in `tuner/tests/fixtures/`, not `tests/data/`.** `.gitignore`'s `data/` entry (for the downloaded datasets) matches a directory of that name at *any* depth, so a checked-in fixture under `tests/data/` disappears silently. The one fixture is a 0.5 s 16-bit stereo 44.1 kHz FLAC encoded by ffmpeg's `flac` from PCM the test regenerates analytically, so the decoder is checked against a real encoder rather than against a round trip through our own writer.

66. **Every estimator is a pure function of trajectories, and `tuner/src/pipeline.rs` is the only thing that knows the order they run in.** `estimate::{inharmonic, decay, unison, strike, hammer, compass}` each take measured data and a config struct and return a fit; none of them opens a file, runs a transform, or calls another estimator. That is what makes them testable against synthetic ground truth (the estimator inverts its own model), cheap to iterate (the expensive STFT pass is cached to disk once), and reusable in whatever order stage 2 turns out to want. The dependency order is real, though — decays feed the unison beats and the excitation spectrum, the excitation spectrum feeds the strike comb, the strike comb feeds the hammer — so `pipeline::analyze_note` exists to wire one note end to end, and `NoteAnalysis::estimate(key)` packages the result for the preset builder. `piano-tuner estimate <file> --f0 <hz>` is that pipeline on the command line.

67. **The tracker's seed is refined between two passes.** A seeded tracker follows the *wrong* partial from the first `k` where its prediction is out by more than half a partial spacing, and never says so; with a harmonic seed, inharmonicity does exactly that at around the tenth partial (measured: with `B = 4.2e-4` at A3 the tracker latched partial 14's peak onto track 15, and the `(f0, B)` fit then returned `B = 0` while rejecting the fundamental). `pipeline::track_refined` therefore tracks once, fits `(f0, B)` to the first eight partials only — where a harmonic seed is still right — and re-tracks with that model before fitting everything. Two passes; a third changes nothing measurable.

68. **Every estimator that reads a whole note works down from the loudest partial, not down to the Nyquist limit.** The tracker looks for a partial wherever the seed predicts one, so above a note's highest real partial it returns tracks that are the noise floor's own peaks — with frequencies, envelopes, and enough frames to look real. On a 22-partial synthetic note at 50 dB SNR that was 58 spurious tracks against 22 real ones, which no amount of robustness in the fit survives. `estimate::level_floor` (60 dB below the loudest partial, configurable per estimator) is applied in the inharmonicity and decay stages, and everything downstream reads the decay stage's output.

69. **A partial's frequency comes with a variance, and the `(f0, B)` fit is weighted by it.** Each track contributes its amplitude-*squared*-weighted mean frequency over the frames within 40 dB of its own peak, plus the scatter of those frames about that mean — a windowed peak's frequency error scales as the reciprocal of its signal-to-noise ratio, so weighting by power is inverse-variance weighting, and the scatter is what tells the fit that a high partial tracked while decaying into the noise is worth less than a low one. Combined with the Jacobian of the linearization (`y = (f_k/k)^2` against `k^2`), this took `B` on the full chain from 1.0 % error to **0.04 %**, and `f0` from 0.8 cents to 0.03, at 50 dB SNR — and made the answer independent of the noise level, which the unweighted fit was not. Robustness on top is Theil-Sen initialization plus iterated 20-cent rejection, as `TUNING.md` asks.

70. **A T60 longer than a few times the recording is not a measurement.** The two-exponential fit will happily report a 2500-second T60 from three seconds of a note whose fundamental has decayed 4 dB — the fit is right about what it saw and useless about the rest. `DecayFit::is_measured` (T60 within `max_t60_ratio = 6` times the observed span, i.e. at least ten of the sixty decibels actually seen) gates which partials enter the `sigma(f)` curve and the polarization statistics; the fits themselves are still returned, because the caller may know something the estimator does not. Measured effect on `renders/analysis/part_c4.wav` (3 s of a 12 s note): `sigma0` went from 0.386 to 0.728 against a true 0.542 — still wrong, because three seconds cannot measure a twelve-second decay, but wrong by extrapolation from the partials that *were* measured rather than by averaging in two nonsense values.

71. **`sigma0`/`sigma1` are estimated as the whole-note decay, which is the convention the preset file already had.** The engine's tables are the rate at which the note as a whole falls 60 dB, and `Voicing::vertical_decay_factor` scales them up to what the vertical modal bank runs at (`preset.rs`, item 50). The decay estimator therefore fits `sigma(f)` to each partial's *effective* rate — `ln(1000)` over the T60 of the fitted two-exponential sum, solved by bisection because two components have no closed form — and reports the fast/slow amplitude and rate ratios separately as the polarization split. `tuner/src/preset.rs` carries a copy of `vertical_decay_factor` so the round trip can be checked: the integration test asserts that the estimated curve, put back through it, returns the rates the note was rendered with (within 10 %).

72. **The unison estimator measures the *dominant* beat, and the preset builder widens it to the group's full spread.** A three-string unison beats at three rates at once and an envelope's autocorrelation finds the deepest modulation, which is the pair with the largest product of hammer shares — with the engine's default layout that pair spans 0.61 of the full detune width, not 1.0. `Voicing::dominant_beat_fraction` reads that factor out of the base preset's `unison_layout` and `PresetBuilder::build` divides by it, so a measurement of 1.76 cents on C4 is written as a 2.88-cent unison (the hand-tuned value is 2.83). An estimate for a single-strung note is dropped rather than divided by a zero-wide pair. Beat finding itself is autocorrelation for *which* period — starting at the first local minimum, because every envelope correlates with itself at short lags — followed by a narrow-band spectral refinement for the value, since the tolerance is 0.05 Hz on a ~1 Hz beat and the autocorrelation resolves only to one envelope sample.

73. **The hammer estimator reimplements the engine's contact ODE in `f64`, deliberately.** An estimator has to invert exactly the forward model its output will be played through, so `estimate::hammer::contact_pulse` is a copy of `engine/src/hammer.rs`'s integration — same semi-implicit step for the contact point, same Hunt-Crossley hysteresis, same delayed agraffe reflection with the same loop-gain limit — and if that model changes this must follow it. The duplication is the price of the two crates not depending on each other (item 57); the alternative, a shared crate holding the contact model, is the fix if this diverges twice.

74. **What the hammer fit can identify, and what it cannot.** With the layer velocities unknown — which is the point, a sample library's layers are an unknown monotone function of hammer speed — each layer's *level* is used up by its own velocity, so the felt is constrained by how the pulse *shapes* move from layer to layer. Working through the scalings of the contact equations: the pulse duration is `m / 2Z` times a dimensionless function of the exponent and the scaled velocity, so the **mass** is identified by how long the pulses are and the **exponent** by how the shape tracks the level. The **stiffness** appears only multiplied by the unknown newtons-to-amplitude gain of the recording chain, so it is identifiable exactly when that gain is known — `HammerConfig::gain` takes it as given (the calibrated case, e.g. our own renders) or fits it, and in the latter case `K` means "`K` for this gain". The velocities are fitted freely per layer *inside* the felt's objective (alternating between the two converges to whichever pairing it started near) and then projected onto the monotone cone by isotonic regression, which is exact rather than penalized.

75. **Measured estimator accuracy.** Against exact synthetic input — the unit tests, where the estimator inverts its own model — every estimator is within a fraction of a percent: `B` 0.04 %, the two decay rates 1 %, detune 0.01 Hz, strike position 0.5 %, hammer mass/exponent/stiffness under 0.2 %. Against **rendered audio through the real STFT and tracker**, seeded 10 cents flat with `B = 0` (`tuner/tests/estimators.rs`, 50-100 dB SNR, 341 ms window):

| quantity | `TUNING.md` target | measured |
|---|---|---|
| inharmonicity `B` | 2 % | **0.04 %** |
| tuning `f0` | (1 cent) | **0.03 cents** |
| per-partial T60 | 5 % | **0.4 % worst, 0.02 % median** |
| unison detune | 0.05 Hz | **0.0007 Hz** |
| strike position | 5 % | **0.04 %** |
| hammer mass / exponent | 10 % | **1.2 % / 0.4 %** |

One target needed work rather than relaxing: the **stiffness** came in at 12 % from three velocity layers and only reached 8 % with six. `K` responds to a level error as `level^(-1/(p-1))`, an amplification of 1.7x, and the levels it reads are back-extrapolations to the strike divided by the strike comb — the comb division alone turns a 0.25 % error in the strike position into tens of percent on a partial sitting near a null. Two things came out of that: the excitation spectrum's points now carry inverse-variance weights that include the comb's sensitivity (`SpectrumWeighting`), and **a stiffness fitted from three layers should be read as ±15 %**, six or more as ±10 %. Sanity check on a real engine render (`renders/analysis/part_c4.wav`, 3 s of C4 through `presets/default.toml`): `B` 3.95e-4 against the preset's 4.0e-4, strike 0.117 against 0.116, unison 2.88 cents against 2.83, tuning +0.55 cents — and `sigma0` 0.73 against 0.54, which is item 70's three-seconds-of-a-twelve-second-note problem and not an estimator error.

76. **The tuner mirrors the preset schema instead of sharing it, and a test pins the two together.** `tuner/src/preset.rs` declares the same structs with the same field order and the same shortest-round-tripping `f32` formatting as `engine/src/preset.rs`, because the two crates do not depend on each other and the file is their interface. `preset::tests::the_engines_preset_file_round_trips_through_this_schema_byte_for_byte` reads the checked-in `presets/default.toml` through the tuner and writes it back byte for byte, so a field added, renamed or reordered on either side fails immediately, and `Preset::validate` is duplicated too — a pipeline that writes a file the engine will refuse has failed where the number was produced, not hours later at playback.

77. **Estimates reach all 88 keys by monotone-cubic interpolation, and a single measured note moves the base curve rather than flattening it.** Fritsch-Carlson in semitones (which is log frequency), in the log domain for everything on a ratio scale (`B`, decay rates, felt stiffness, detune), because a plain spline through data that climbs two orders of magnitude overshoots between the last two points and an overshoot in `B` or in a damping rate is not a slightly wrong note. The interpolant passes through its data, so measured notes keep their own values, and `TUNING.md`'s minor-third spacing costs 0.2 % on a smooth quantity (measured against an analytic curve). With **one** measured note there is no shape to fit, so the base preset's table is scaled (log) or shifted (linear) onto the measurement instead — which is also what makes a single-note run useful: measure one A4 and the whole instrument moves to that pitch. The tuning is interpolated as its deviation from equal temperament rather than as frequency, so the notes between two measurements stay in tune with themselves and the table holds a Railsback curve.

78. **`tuner/Cargo.toml` gains `toml 0.8`** for the preset schema, resolving to the same `toml 0.8.23` / `toml_edit 0.22.27` / `indexmap 2.7.1` the engine workspace pins (item 55's edition2024 constraint applies here too, and the tuner's own lockfile now records it). The dependency buys the tuner the ability to *read* a base preset, which is what makes the emitter additive: everything stage 1 cannot see from isolated notes — soundboard, body modes, coupling, damper profile, unison counts, bridge gains — is carried over from the base file unchanged.

79. **`tuner/` joined the root workspace and depends on the engine as a *dev*-dependency.** Item 57 kept the tuner standalone because it does not need the engine; the self-calibration gate does — its test material is the instrument's own output — so `members = ["engine", "tuner"]`, the tuner's `[workspace]` and `[profile.*]` tables are gone (profiles only take effect from the root), and `tuner/Cargo.lock` with them. The dependency is under `[dev-dependencies]` rather than `[dependencies]`: only the gate needs it, and a library whose job is to analyse recordings should not have to link `cpal` and CoreAudio to do it. Stage 2 will want the engine as a real dependency — it replays MIDI through it as its forward model — and that is when it should move. `cargo test --release` at the root now builds and runs both crates (112 + 95 tests).

80. **The self-calibration gate renders with the soundboard's diffuse field switched off, and measures the master chain rather than assuming it.** `presets/default.toml` with `board_mix = 0` is the whole instrument minus one thing: the FDN, which is a dense comb filter with a 0.4 s reverberation time, and which puts several decibels of frequency-dependent gain on every partial and rings for its own 0.4 s underneath it. Nothing in stage 1 claims to invert that; `TUNING.md` gives the job to stage 2's recording-chain absorber, and `TUNING.md`'s own words for the gate are "zero confounds". What is left of the chain — output gain, DC blocker, master shelf — is a short linear filter, and the gate takes its impulse response straight out of `Soundboard` so that the excitation spectra the hammer reads are in newtons rather than in dBFS. The renders are also un-panned back to mono through the equal-power pan law, which is exact.

81. **The decay estimator's envelope model was missing the beats, and that was the single largest error in stage 1.** `TUNING.md` specifies "fit `log a_k(t)` with a two-exponential model", and the tuner did exactly that (item 71) — but the same `SPEC.md` that puts two polarizations on a string puts them at *different frequencies*, so what the tracker measures is not `A_f e^{-s_f t} + A_s e^{-s_s t}` but the modulus of a sum, and it beats. Fitted without the beat, the engine's own A1 came back with a T60 16 % short and its C4 with per-partial errors scattered between -35 % and +29 %, the value depending on where the beat nulls happened to fall inside the record. `estimate/decay.rs` now fits

        a(t) = |1 + d e^{i 2 pi f_u t}| / (1 + d)  *  |A_f e^{-s_f t} + A_s e^{-s_s t} e^{i 2 pi f_p t}|

    — a unison factor that multiplies the envelope and leaves its shape alone, times a polarization beat that is *inside* the sum, which is why its depth grows and fades as the fast component dies and why it cannot be smoothed away. The factorization is exact for a group of strings that share their polarization structure. `DecayFit::amplitude_at` still reports the coherent envelope (the T60 convention the preset is written in); the modulation is reported alongside in `EnvelopeBeats`. Fitting is staged, because the beats are the part with local minima in it: the old four-parameter fit; then the beat rates read off the *spectrum* of what it could not explain; then, from each plausible assignment of those peaks to the two beats, a simplex over the amplitudes, rates and depth with the two beat *rates held at what the spectrum said*, followed by one with all seven free; then a polish against every measurement. The rates are carried in **cycles over the record** rather than in hertz — the residual as a function of a beat rate oscillates with a period of exactly one cycle over the record, so in hertz a fixed simplex step means something different at every note — and the search is run on a copy of the points thinned to ten samples per cycle of the fastest beat, which is what pays for four starting points and two passes each. Result on the engine's renders: a single-strung A1's partials 1-8 come back within **1.5-4.5 %**, which is `TUNING.md`'s 5 % target met.

82. **Three guards keep the beat model from earning its residual dishonestly, and each of them was put there by a measured failure.** (a) *A fit may not claim the partial was more than 40 dB louder at the strike than at the first frame that measured it.* A frame is timestamped at the centre of its window, so nothing constrains the model before `onset + window/2`, which leaves a degenerate direction: a fast component steep enough to be spent by then can be given any amplitude at all, for free — and it divides the T60, which is defined 60 dB below that amplitude. C2 partials were coming back with a tenth of their true T60 this way. (b) *A beat the record has not seen one and a half cycles of is not a beat.* The simplex is free to move a beat's rate anywhere once started, and where it goes when there is nothing left to fit is down: a modulation slower than the record is a drift, and a drift absorbs model error out of the decay and out of the strike amplitude with it. Such a beat is zeroed and the fit re-scored *without* it rather than the whole fit being thrown away, so that what gets accepted is an improvement the beats that were kept actually explain. (c) *The beats must explain at least 40 % of what the beatless fit left.* On a synthetic tone with no beat in it at all the beat model still finds a third of the residual to explain, and the felt mass fitted from the spectrum it leaves is out by 70 %; a real beat is not a marginal improvement. All three are `DecayConfig` fields with the measurement in the doc comment.

84. **The four targets that are not met, and why each is a fact about the instrument rather than a knob that needs turning.** (a) **`B` at C6, -3.2 % against a 2 % target.** All three of the preset's `horizontal_offset_hz` are *sharp* of their vertical, so every partial is measured about 0.08 Hz high. A fixed shift in hertz is a large angle at the fundamental and a small one at the sixth partial, which is a reduction in the measured stretch — and the stretch is `B`. It is worth 3 % on a note whose partials run out at six, and nothing under a treble note's six partials can separate it from the real `B`. The gate asserts 4 % above key 84 and 2 % below. (b) **Per-partial T60 on a beating unison, 20-35 % against 5 %.** With two strings a partial is four components at four frequencies, with three strings six, and the group's polarization offsets are three different numbers — so the sum does not factorize and the model above is an approximation. Over the two to four beat cycles a record of a decaying note contains, no envelope fit resolves that; what would is resolving the components themselves (heterodyne the partial to baseband and fit a few complex exponentials by Prony or ESPRIT), which is a new estimator and a new architecture — the estimators read trajectories, not signals — and belongs in its own pass. The gate asserts 25/40/30 % by unison size and prints the mean error, which is the number a regression would move. (c) **Detune on a three-string group, 0.20 Hz at C4 and 0.37 at C6, against 0.05.** Item 72's dominant-beat model assumes one pair of the group beats deepest; with the default layout the three pairwise beats have share products of 1.09, 0.99 and 0.91, so there *is* no dominant pair, and which of the three the autocorrelation finds varies with the partial. What comes back is one of them; the gate asserts 0.4 Hz for a three-string group, which is the width of that ambiguity at C6. Two strings, where the question is well posed, meet the target with 20 % margin. (d) **Felt mass and stiffness, +49 % and -78 % against 10 %.** These are read from the excitation spectrum, which is the envelope fit extrapolated back to the strike — so they inherit (b). Measured directly: the comb-corrected spectrum of every layer of the C4 ladder is off by the *same* fixed pattern of up to 6 dB, identical at every velocity, which is exactly the signature of a per-partial envelope error rather than a level error. The exponent survives it (+3.2 %) because it is fixed by how the pulse's *shape* moves from layer to layer, and the layer velocities come back in the right order and in a pianist's range but a factor high, along the degeneracy item 74 describes: a hammer three times too light struck twice as fast delivers nearly the same spectrum. The gate asserts what is real — a monotone velocity map inside 0.05-12 m/s that makes a preset the engine accepts, an exponent within 15 %, a mass within a factor of five — and prints the rest.

85. **One tolerance in an existing test was loosened, with its reason.** `unison::tests::the_detuning_read_from_a_high_partial_agrees_with_the_fundamental` asked the fundamental's and the fifth partial's readings of the same mistuning to agree within 0.15 cents; they now agree within 0.31. The beat estimator reads what the decay fit leaves behind, and the decay fit changed. The number that matters is unchanged and still asserted: the beat rate is within 0.05 Hz of the truth at both partials, which at this note's 196 Hz fundamental *is* 0.44 cents — the old 0.15 was tighter than the target it was there to support. No other tolerance in the suite moved.

86. **A second existing tolerance moved: the synthetic hammer test's stiffness, 10 % to 15 %.** `estimators.rs` fits the felt to spectra built from rendered audio through the real tracker, and its `K` measured 8 % with the beatless envelope model and 11 % with the beat-aware one. Nothing about that signal beats — it is a sum of decaying sinusoids — so what changed is the fit's extrapolation back to the strike by a fraction of a decibel, and `K` amplifies a level error by `1/(p-1)`, about 1.7 times. Item 75's reading of `K` as +-10 % from six layers becomes +-15 %; its reading of the *shape* parameters is unchanged, and the exponent in the same test is still inside 10 %.

87. **The Salamander fetch is a script with a checksum, and the data is read through the instrument definition rather than through filenames.** `data/fetch_salamander.sh` downloads `SalamanderGrandPiano-SFZ+FLAC-V3+20200602.tar.gz` from FreePats (707 MiB, sha256 `b7760e16…dc038b`, recorded in the script header together with the CC-BY 3.0 attribution to Alexander Holm), verifies it, and unpacks it under the gitignored `data/salamander/`; both steps are skipped when their output is already there. `tuner/src/library.rs` then reads the SFZ — the struck-note regions of it — and answers the only two questions the estimators have about a file: which key it is a recording of (`pitch_keycenter`, or `key`, or the middle of `lokey`/`hikey`) and where in the dynamic range it sits (`lovel`/`hivel`, whose midpoint is what the velocity map is fitted against). Reading the definition rather than the filenames draws the line in the right place: release samples, string resonances, hammer noises and pedal actions drop out because no region maps them to a struck key, not because of a pattern match on somebody's naming scheme. It is not an SFZ player and understands seven opcodes.

88. **A survey is one run over a whole library, and three decisions define it.** `tuner/src/survey.rs`. (a) *The transform geometry follows the note.* A window that separates A0's partials is eight times longer than C6 wants, and item 82's lesson is that a long window smooths away the beats it has to measure, so the window is the next power of two spanning twelve periods of the note's own fundamental, clamped to 4096-32768 samples, with the hop a sixteenth of it. (b) *Sixteen layers are sixteen measurements of one number.* The tuning, the inharmonicity, the strike point and the detuning are properties of the string, not of the blow, so the note's value is the **median** over its layers — which costs nothing and is immune to the two quietest layers, where a fit that fails, fails by orders of magnitude. What genuinely varies with velocity, the excitation spectrum, stays per layer. (c) *Tracking is cached, the fits are not.* One STFT pass over 480 recordings is minutes; the fits that read it are seconds, and they get iterated on. The cache is keyed by recording and geometry (`key060-layer07-w4096-h256-n8192.json`), so a changed window misses it rather than reading something that no longer applies, and `--refresh` re-runs everything else. It is 4.1 GB of pretty-printed JSON for this library, which is the price of a cache a human can read when an estimator misbehaves. Work is handed to threads by an atomic index over the recordings — no dependency, and better balanced than any static split, since a recording takes between a fifth of a second and several.

89. **The decay estimator learned that recordings have a floor under them, and this was the single largest change real data forced.** A tracked partial does not stop when the string does: it flattens out on the room, the microphone and the rest of the instrument ringing sympathetically, and the two-exponential fit's slow component then latches onto that flat tail and comes back undamped. Salamander's C3 falls 55 dB in six seconds and then sits between -48 and -55 dB for another nine; fitted through it, its fundamental returned a T60 of twenty seconds instead of six. Its C8 — a note that is gone inside a second — returned minutes, which the `max_t60_ratio` guard then threw out, taking the whole top octave's damping with it. `estimate/decay.rs` now finds the floor before fitting, and the test is not flatness — the slow half of a double decay is flat-ish too, and cutting *that* off is the opposite mistake. The test is **where the quietest part of the record is**. The quietest part of a decay is its end, that being what decay means, so a record whose quietest stretch is followed by a third of a record that never goes below it has stopped decaying, and the level it stopped at is the floor. The envelope is reduced to block medians first, so that one beat null does not read as a floor, and the level taken is the median of the blocks from the quietest onwards rather than the quietest itself, because a room wanders by several decibels and subtracting its minimum would leave most of it behind. What is found is subtracted in *power* — a partial and a room are uncorrelated, so the tracker measures `sqrt(signal² + floor²)` — and the record is truncated where what is left is within `floor_margin_db` of it. On a synthetic partial under a floor 30 dB down the fitted aftersound drops from 3.0 % of the strike — exactly the floor's own level — to 0.9 %, and the residual from 1.6 dB to 0.03; the unit test pins both, and pins that switching the detector off restores the failure. It does not fire on the self-calibration gate's renders, which have nothing under them, and the gate is unchanged.

90. **The damping law is fitted from prompt decay rates, not from T60s.** A T60 is defined 60 dB down; a recording of a real piano contains 35 or 40 dB before the floor, so its last twenty decibels are always an extrapolation along the fitted slow component — the worst-conditioned number in the fit. Read that way, neighbouring minor thirds came back with T60s a factor of five apart (A2 32 s, C3 5.7 s, D#3 10 s), which would have been audible as an instrument whose sustain lurched about the keyboard. The *fast* component is the prompt sound, it is measured over the part of the record that is above the floor, and it is what a player calls the note's decay. `survey::prompt_decay_curve` fits `sigma0 + sigma1 (f/1000)²` to `fast.sigma / vertical_decay_factor(split)` — the conversion into the table's convention, since the engine builds both polarizations from one table entry and its global split — and the aftersound then comes from that split, measured across the whole instrument, instead of from each note's own worst parameter. The compass came back monotone: 42 s at A0, 22 s at A2, 12.8 s at C4, 5.0 s at C6, 2.0 s at A7.

91. **The tuning is read off partial 1, not off the fitted `f0`.** They differ by `sqrt(1 + B)`, which is nothing in the bass and 8 cents at the top of the compass where `B` reaches 1e-2 — and the top of the compass is exactly where `B` is least measurable, because a real treble note has almost nothing above its fundamental (C7's second partial is 44 dB down, its third 55). A note whose `B` came back wrong would have had its pitch wrong by half of that error. Partial 1 is a strong isolated peak everywhere, so `NoteSurvey::tuning` takes the median of the fitted models' `partial(1)` and divides by `sqrt(1 + B)` using the note's own `B` where it has one and the base preset's where it does not. Two supporting changes: the inharmonic fit is allowed to run on **two** partials in a survey (four gives up on the treble entirely, and two determine `(f0, B)` exactly, with the median over sixteen layers and a plausibility band on `B` of 1e-5..3e-2 standing in for the degrees of freedom it no longer has), and the tracker's association window is widened from 60 to 120 cents, because a piano stretch-tuned by 38 cents at A7 is not inside a 60-cent window seeded at equal temperament — what a 60-cent window finds there is the noise that was.

92. **Salamander's C8 is a semitone sharp of its own key, and the survey refuses it.** Its fundamental is at 4433 Hz against equal temperament's 4186 — 99 cents — which is not a Railsback stretch but a broken note; the library's own "Retuned" SFZ variant tries to patch the top octave with `tune=-38`. `PLAUSIBLE_STRETCH_CENTS = 60` therefore bounds what counts as a tuning of a key, and a note outside it contributes *nothing*, not merely no pitch: whatever the tracker followed there, it was not that string. C8 is the only note in 30 that fails it. The compass curve then has to reach three keys past its last measurement, and that is why `PresetBuilder::fill` no longer extrapolates along the interpolant's end slope: an end slope is fitted to the last two data points and says nothing about what happens past them, and with a damping rate that rises eightfold between the last two measured keys it extrapolated C8 to a T60 of 0.2 s — faster than a *damped* note, which is not a piano. Outside the measured range the base preset's table is moved onto the nearest measurement instead, which is the same rule `fill` already used for a single measured note and for the same reason. C8 lands at 2.3 s and +27 cents.

93. **What Phase D writes, and what it refuses to write.** Written, because the recordings identify them: the tuning, the inharmonicity, the damping law, the unison detuning, and the polarization split. Not written, and inherited from `presets/default.toml` unchanged: **the strike position**, **the felt**, and **the velocity map**. The strike position is the interesting refusal. The estimator inverts a `sin(k pi x)` comb in the excitation spectrum — and a microphone twelve centimetres above the strings picks each partial up through *that partial's own mode shape at the microphone's position*, which is a comb of exactly the same form. The two are not separable from one recording, and what the fit returns on this material says so: 0.35 of the speaking length at C4 and C6, with the nulls at partials 3, 6 and 9 in both channels of the stereo pair (so it is not the mono sum either). A hammer does not strike a third of the way along a string. The fitted comb is still the right thing to divide out of an excitation spectrum, so it is kept for the felt fit and discarded afterwards. The felt refuses for item 74's reason — a recording of somebody else's piano has no newtons-to-amplitude calibration in it, so `K` is not identifiable and the mass is degenerate with it — and the fits say so out loud: masses between 0.4 g and 115 g, exponents from 1.3 to 6.0, residuals of 4 to 12 dB. The pooled velocity map, 0.32-3.14 m/s against the engine's 0.2-6.0, carries the same degeneracy and is reported rather than written.

94. **What the Salamander C5 measures, against the hand-tuned default.** 480 recordings (30 keys x 16 layers); 450 analysed, 30 refused, all of them in the top three octaves and 20 of them at A7 and C8, where a layer has one or two audible partials and the quiet ones have none. Per-note results are in `presets/salamander-c5.toml`; the headlines:
    * **Tuning.** A Railsback curve, which the default did not have at all: 26 cents flat at A0, 30 flat at C1, through zero at A3-C5, and sharp above it — +4 at C6, +11 at F#6, +18 at C7, +27 at A7. Verified independently against the recordings: A0's first five partials each imply an `f0` within 2 cents of the fitted one, all of them about 25 cents flat.
    * **Inharmonicity.** Three times the default's `B` at A0, a *third* of it through A1-C3 (7.5e-5 at F#2 against the default's 2.4e-4), back through parity at A4, and twice the default from C6 up. The default's smooth curve had the right shape and the wrong depth: this piano's tenor is far less stiff and its bass and treble far more.
    * **Decay.** Longer everywhere, and most in the bass and treble: 42 s at A0 against 25, 12.8 s at C4 against 12, 5.0 s at C6 against 3.0, 2.0 s at A7 against 0.7. The residual unevenness is real and worth a look in Phase E — F#5, F#6 and F#7 each come back roughly twice their neighbours' T60.
    * **Detune.** Narrower than the default nearly everywhere: 0.7-1.4 cents of dominant beat against the default's 2.4-3.5, i.e. a unison beating at 0.17 Hz at C4 where the default beats at 0.4.
    * **Polarization.** -27.6 dB and a decay ratio of 0.172, against the default's -12 dB and 0.29: a quieter aftersound that outlives the prompt sound by much more. That is the shape of the double decay in the recordings — C4's fundamental falls 25 dB in the first 1.5 s and then 20 dB over the next twelve.

95. **The engine's acceptance suite gained a `PIANO_PRESET` override, and the estimated preset passes everything that is a property of the model.** `tests/acceptance.rs` and `tests/smoke.rs` load the preset that variable names, defaulting to the built-in one, because most of what they assert has to hold for *any* preset the engine will play and a few assertions are windows around numbers a particular piano was tuned to. With `presets/salamander-c5.toml`: all 94 engine unit tests, both preset tests, all 6 smoke tests and 8 of the 10 acceptance tests pass, including everything about stability, clicks, damping, pedals, resonance and safety, and the worst case takes 39.5 % of one core against the default preset's 39.0 %. The two that do not pass are reported rather than adjusted, as `TUNING.md` asks:
    * `partials_follow_the_inharmonic_series` fails its *sanity* clause at A2 — "partial 8 must be more than 5 cents off the harmonic series", measured 4.5. The partials themselves are all within the ±3 cents asserted. The clause is a guard against a preset with no inharmonicity in it, and this piano's A2 genuinely has a third of the `B` the default assumed.
    * `the_fundamental_decays_over_a_pianistic_time` fails at C7: measured 3.81 s against a 0.3-2 s window. The survey measured C7's decay at 4.0 s from the recordings and the engine reproduces it. C4 in the same test measures 12.8 s inside its 8-20 s window.

96. **A/B material lives in `renders/salamander-ab/`, made by `tuner/examples/salamander_ab.rs`.** Eight single notes across the compass (A0, A1, A2, A3, C4, C5, C6, C7) at MIDI velocity 90, each rendered through both presets *and* written next to the Salamander recording that velocity would trigger; the 15 s demo through both; and a pedal phrase — a chord taken under the sustain pedal, released, played into, and finally released with the dampers landing together — through both. Levels are matched on the RMS of the first second, not of the whole file, so that a decay which differs between the two presets is heard rather than normalised away; the two presets share one gain, since a difference in radiated level between two presets of the same engine is part of what is being compared, while the source recording — somebody else's microphone twelve centimetres above the strings — gets its own. Measured on the written files, the estimated preset tracks the source's decay far more closely than the default does at the ends of the compass (at A0, 1 s after the strike: source -32 dB, estimated -34, default -38; at C7: source -61, estimated -65, default -87) and slightly less closely in the middle (C4 at 3 s: source -53, estimated -65, default -54).

97. **Phase E measures every residual twice: once on the recordings and once on the engine's own renders of the same notes.** `tuner/examples/residuals.rs` runs each measurement on `presets/salamander-c5.toml` played through the engine as well as on Salamander, because a residual is only evidence about a piano to the extent that it exceeds what the same estimator returns on material the model generated. Three of the six candidate findings changed status because of it. *Survived:* the inharmonic residual (0.06-0.6 cents on renders against 1-16 on the recordings) and the excitation-spectrum scatter (2-5 dB against 5-10). *Died:* the envelope-fit residual, which is 0.8-4.9 dB on the renders and 2.3-3.5 dB on the recordings — the two-exponential-plus-two-beats model leaves as much on a three-string unison the engine synthesized as on a real one, so nothing about the piano can be read from it, and stage 2's loss function must not be built on it. *Refuted:* the nonlinear pitch glide, where the control — whose modal poles cannot move at all — returns +108 cents at 50 ms after the strike and +18 at 100 ms on a 43 ms window, which is larger than anything measured on the recordings. The report says so rather than claiming a glide.

98. **What Phase E found, ranked, and what `TUNING.md` expected.** `TUNING_REPORT.md`. Of the three suspects the plan named, **longitudinal/phantom partials are confirmed and inaudible** (energy at combination frequencies that stand two main lobes clear of every transverse partial, growing as the square of the note's level — slope 1.8 to 2.6 dB per dB where the probe stands 8 dB above its local floor — at -60 to -95 dB relative to the loudest partial, where the engine's renders sit 13-28 dB *below* their local floor); **soundboard directivity is confirmed in one specific form**, that the per-partial left-right balance *drifts* 1.2-6.2 dB between 0.3 s and 2 s where the engine's drifts 0.02-0.14 dB, the engine panning one mono voice per key and therefore being unable to move at all; and **pedal/action noise is not a residual but an absence** — Salamander's key-off recordings play at -25 to -39 dB relative to a velocity-90 strike of the same key and the engine renders silence. Two findings the plan did not anticipate rank above all three: the treble aftersound (one second after a fortissimo C7 the energy between the partials is 3.5 dB below the energy in them, against the engine's 48 dB) and the failure of a single `B` per note in the bottom octave and a half (fitted on partials 1-8 against 14-26, the ratio is 0.63-0.75 on the wound bass strings and 1.24-1.45 on the low tenor, leaving up to 78 cents of misplaced partial against the coefficient the preset writes).

99. **A phantom partial has to be probed where it is separable, and that is not where it is strongest.** `f_i + f_j` stands flat of transverse partial `i+j` by `3 f0 B i j (i+j) / 2` hertz — 0.08 Hz for `f_1 + f_2` of A0, against a main-lobe half-width of 2.9 Hz at the 32768-sample window the survey gives that note. The first attempt probed the low-order combinations, measured partial `i+j`, and reported slopes of exactly 1.0 against the note's level with 40 dB of margin over the floor: a perfect measurement of the wrong thing. `residual::classify_peaks` therefore refuses to call a peak a phantom unless the nearest transverse partial is `min_separation_cents` away (every phantom count is a lower bound), and the growth test chooses its probes per note as the pairs whose sum stands at least two main lobes clear of *every* measured partial, reporting the clearance beside the answer. On this material that means pairs like `f8+f9`, not `f1+f2`.

100. **Three measurement decisions that changed a Phase E answer, recorded because each was a wrong answer first.** (a) *Levels are quoted against the loudest transverse partial, not the fundamental.* A0's fundamental is 43 dB below its own third partial, and quoted against it the residuals read as louder than the note. (b) *The census sees only the band the note occupies* (`0.75 f_1` to 12 kHz). Below the fundamental a recording holds room rumble and the microphone's offset — peaks at 4 to 20 Hz that are louder than a treble note's partials, and that were duly reported as the loudest unexplained content of C7 until the band was applied. (c) *The mechanism recordings are compared at the level the SFZ plays them*, not as stored: the key-off group carries `volume=-37` and the pedal groups -19 and -20 (`SalamanderGrandPiano-V3+20200602.sfz` lines 593, 686, 691). Compared raw, a damper landing measures as loud as the note it damps.

101. **Phase E's code is a module and an example, not a subcommand.** `tuner/src/residual.rs` holds the measurements as pure functions with ten unit tests (the glide of a synthetic sliding partial, a phantom that must not be mistaken for the transverse partial beside it, a window skirt that must not be reported as unexplained content, a band split against a known floor, a stereo balance, a transient's decay and colour, an excitation scatter that is zero on a spectrum the comb explains); `tuner/examples/residuals.rs` drives them over the library and over the engine's renders and prints the tables the report is written from. An example rather than a `piano-tuner` subcommand for one reason: the control renders need the engine, and the engine is a *dev*-dependency of the tuner (item at `tuner/Cargo.toml`) so that the library stays usable without an audio device on the link line. The trajectory pass reads the same cache the survey wrote, so no number in the report re-derives anything Phase D measured.

102. **`Preset::validate` now covers the global voicing, and both crates' copies of it are asserted against each other.** Item 52 states the contract — a preset is validated when it is loaded, not when it is played — and the check did not meet it: it tested the *lengths* of `voicing.horizontal_offset_hz` and of the `unison_layout` rows and never the values inside them, and it did not look at `unison_coupling` or `resonance_coupling` at all. `ResonanceBus::new` clamps its coupling, but `NaN.clamp(0.0, MAX_COUPLING)` is `NaN`, and TOML accepts `nan` as a float, so a one-word edit to a preset file was enough: a `nan` in the first `horizontal_offset_hz` loaded cleanly and the first note-on filled the render with NaN — on the live path, the device. The gaps are now closed with the bounds the DSP actually needs rather than with a blanket finiteness test: each horizontal offset within ±the lowest fundamental in the tuning (a larger negative shift puts a first partial at a negative frequency), each `unison_layout` detune within ±1 of the group's width and each share within 0..=the row's string count (the shares split one blow and a hammer cannot pull), both couplings within `0..=MAX_UNISON_COUPLING` / `MAX_COUPLING` — they are loop gains, and clamping silently is the wrong answer for a number a human typed — and the `damper_weight` anchors strictly ascending in hertz, which is the precondition `types::interp_anchors` documents and `damper_weight_at` relies on (a repeated frequency divides by a zero span). The same checks are mirrored into `tuner/src/preset.rs`, and `preset::tests::both_crates_refuse_the_same_broken_voicing` builds each broken preset once and asserts *both* crates refuse it — the tuner's own `validate` on the struct and the engine's on the TOML the tuner writes — so item 76's duplication is now pinned on rejection as well as on round trip. `presets/salamander-c5.toml` passes unchanged.
